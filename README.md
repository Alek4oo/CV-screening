AI CV Screening по EU AI Act

Инструмент за класиране на кандидати спрямо роля — обяснимо, без дискриминация и с човек в цикъла. Изграден като високорискова AI система по EU AI Act (Annex III §4), с комплайънс слой: bias-одит, human-in-the-loop, прозрачност и одитни логове.

⚠️ Всички данни са синтетични. Без реални лични данни или достъп до реални системи.

Функционалности
Парсване и класиране на CV-та спрямо изисквания на роля.
Качване на CV в PDF или TXT, с базов OCR за сканирани PDF-и.
Обяснимо класиране — кои умения/фактори тежат и защо.
Изглед за рекрутер с преглед и ръчно решение (никакво авто-отхвърляне).
Bias-одит: сравнение на класирането със и без чувствителни признаци (пол/възраст/произход).
Одитни логове на всяко решение (вход, изход, версия на правилата, кой е потвърдил).
Архитектура

Модулен монолит (modular monolith) с hexagonal подредба на модулите — едно приложение, един деплой, с ясно обособени вътрешни модули и строги граници между тях. Правилният размер за соло/двама: чистото разделяне на отговорностите от микросервисите, без мрежовата сложност на разпределена система.

Ключови решения:

Сменяеми адаптери (strategy pattern) за OCR (extract_text(file) -> str) и скоринг (score(candidate, role) -> Result) — реализацията се сменя тривиално.
Комплайънс слоят е cross-cutting — маскира защитени атрибути преди скоринга, пуска bias-одита и пише в неизменим одитен лог.
Human-in-the-loop е състояние в потока, не бутон — нищо не става „отхвърлено" автоматично.
Версионирани правила (ruleset_id) — всяко решение сочи към версията, с която е взето.

Поток на данните: качване → OCR → структуриран профил → маскиране на защитени полета → скоринг спрямо роля → обяснение → рекрутер преглежда (HITL) → потвърждава/отменя → запис в audit_log. Bias-одитът работи офлайн върху целия набор.

Защо релационна база

Данните са силно свързани (кандидати ↔ роли ↔ решения ↔ правила ↔ одит), а одитната следа иска ACID и неизменимост — силните страни на релационния модел. Гъвкавите, вариращи CV полета се пазят в JSONB колони; евентуален семантичен матчинг — през pgvector. Всичко в една база, без отделна NoSQL система.

Стартиране

Изисква Docker и docker-compose.

bash
git clone <repo-url>
cd cv-screening
cp .env.example .env
docker-compose up --build

Приложението тръгва на:

Frontend: http://localhost:3000
API + документация: http://localhost:8000/docs

Локално стартиране (без Docker)

Изисква Python 3.11 и Tesseract с езиковите пакети bul+eng. Растеризирането на сканирани PDF-и е на pypdfium2 (колело от PyPI) — системен poppler не трябва.

bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload

Настройките идват от backend/.env (виж .env.example). За бърз старт без Postgres:

DATABASE_URL=sqlite:///./dev.db
TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe # само ако не е на PATH

Качване на CV — приемат се PDF (с текстов слой или сканиран) и TXT. През изгледа е с влачене на файлове (виж по-долу); през API-то:

bash
curl -F "file=@tests/data/sample_cv.pdf;type=application/pdf" http://127.0.0.1:8000/candidates/upload

Роли, правила и класиране

Ендпойнти:

POST   /roles                    създава роля (чернова по подразбиране)
GET    /roles?status=open        изброява роли, с limit/offset
GET    /roles/{id}               една роля
PATCH  /roles/{id}               частично обновяване
DELETE /roles/{id}               само роля без класирания — иначе status=closed
POST   /roles/{id}/rank          класира кандидатите

GET    /roles/{id}/rankings      класацията с решенията, с филтри
GET    /rankings/{id}            едно класиране с обяснението зад него
GET    /rankings/{id}/audit      одитната следа на класирането и решенията
PUT    /rankings/{id}/decision   записва решението на рекрутера

GET    /candidates               изброява кандидатите, с търсене по име/е-поща
GET    /candidates/{id}          един кандидат (без защитените признаци)

POST   /rulesets                 нова версия правила, ражда се като чернова
GET    /rulesets?status=active   изброява версиите
GET    /rulesets/active          версията, която е в сила
GET    /rulesets/{id}            една версия
PATCH  /rulesets/{id}            само чернова
POST   /rulesets/{id}/activate   активира и ретайрва предишната
DELETE /rulesets/{id}            само чернова

Версия, с която е взето решение, не се редактира и не се трие — промяна значи нова версия. Затова редакцията и триенето важат само за чернови, а активирането ретайрва предишната активна, за да е еднозначно коя е в сила. Ролята с класирания също не се трие; затваря се със status=closed.

POST /roles/{id}/rank класира кандидатите по активната версия правила и връща скор + принос на всеки фактор. Ролята казва какво се иска, ruleset-ът — колко тежи:

role.requirements:
{
  "required_skills": [{"name": "python", "weight": 3}, "postgresql"],
  "preferred_skills": ["docker"],
  "min_years_experience": 4,
  "min_degree": "bachelor",
  "languages": ["english"]
}

ruleset.definition:
{
  "weights": {
    "required_skills": 0.50,
    "preferred_skills": 0.15,
    "experience": 0.25,
    "education": 0.10,
    "languages": 0.00
  }
}

Скорът е 100 × Σ(тежест × изпълнение) / Σ(тежест) по факторите, за които ролята има изискване. Изричните тежести са пълни — фактор, който не е изброен, тежи нула. Класирането е в режим masked и сочи към ruleset_id; непокритият минимум вдига флаг meets_minimum=false, но не отхвърля никого.

bash
curl -X POST http://127.0.0.1:8000/roles/<role-id>/rank
curl -X POST http://127.0.0.1:8000/roles/<role-id>/rank -H "Content-Type: application/json" -d '{"ruleset_version": "2026.08.1"}'

Преглед и решение (human-in-the-loop)

GET /roles/{id}/rankings връща записаната класация — не я преизчислява — заедно със статуса на решението по всеки кандидат. Филтрите стесняват показаното, но не местят никого: outcome, meets_minimum, min_score/max_score, q (име или е-поща), sort, ruleset_version.

Позицията се смята върху пълната класация за (роля, версия), преди филтрите. Иначе „покажи само за преглед" би преномерирал кандидатите и рекрутер, видял №3, после би го намерил като №1. Броячите по статус са по същата причина върху пълния набор.

bash
curl "http://127.0.0.1:8000/roles/<role-id>/rankings?outcome=pending&meets_minimum=false"

PUT /rankings/{id}/decision е единственият път, по който кандидат сменя статус. Няма автоматичен вариант: заявката изисква и кой решава, и защо — и двете влизат в Decision и в одитния лог, заедно с версията правила, дала скора.

bash
curl -X PUT http://127.0.0.1:8000/rankings/<ranking-id>/decision   -H "Content-Type: application/json"   -d '{"outcome": "advanced", "decided_by": "ана@sirma.bg", "rationale": "Покрива всички задължителни умения."}'

Статусите са pending → advanced | rejected | on_hold, като връщането към pending също е решение и също иска обосновка. Липсваща обосновка или липсващо име дава 422 и нищо не се записва — на ниво база същото пази CHECK ограничението ck_decision_requires_human.

meets_minimum=false не отхвърля никого. Флагът стои в реда, липсващите изисквания се изброяват до него, и толкова — решението остава на човек.

Изглед за рекрутер (frontend/)

React (Vite + TypeScript) на http://localhost:3000. Интерфейсът е на английски, както и всичко, което API-то връща навън (виж „Език на интерфейса“ по-долу). Три екрана:

Роли — избор на роля, с филтър по статус.
Класация за роля — качване на CV-та, броячи по статус, филтри и таблицата с място, скор, флаг за минимума, водещите фактори, какво липсва и статуса на решението.
Детайл на кандидат — скорът с разбивка по фактори (тежест, изпълнение, точки, покрито/липсва), профилът от CV-то, какво иска ролята, версията правила с тежестите ѝ, панелът за решение и одитната следа.

Качване и оценка на момента

CV-тата се пускат в изгледа на ролята — с влачене или през диалога за избор, няколко наведнъж. Всеки файл минава сам по пътя качване → OCR и парсване → класиране спрямо ролята и показва резултата си веднага: разпознатото име, кой двигател е чел, колко знака е извлякъл, увереността на парсването и получения скор, с връзка към обяснението. Обработката е последователна, защото OCR-ът е скъп и десет едновременни заявки биха забавили и първия резултат.

Отказите се различават по вина, както и в API-то: неприет тип и файл над лимита се спират още в браузъра, нечетимият документ се връща с обяснението на бекенда, а „CV-то е качено, но класирането отказа" се казва отделно — например когато няма активна версия правила. Провален файл не спира останалите в партидата.

Ниска увереност на парсването вдига предупреждение да се провери профилът, преди да се решава по скора: нестандартен формат на CV-то може да е подвел парсера, а не кандидатът да е слаб.

Качването дава скор, не статус. Новият кандидат влиза в класацията като „за преглед" — както всеки друг.

Език на интерфейса

Всичко, което системата казва навън, е на английски: изгледът, съобщенията при отказ (detail на HTTPException), обяснението на всеки фактор (ranking.explanation.detail) и описанията в /docs. Коментарите и докстринговете в кода остават на български — те са вътрешни.

На български остава само това, което е данни, а не текст на системата:

Съдържанието на CV-тата — имена, степени („магистър“), езици („Български“). Такова е и в оригиналния документ; изгледът го показва както е.
Обосновките, написани от рекрутера — те се пазят дословно.
Речникът в app/parsing/vocabulary.py — с него се разпознават български CV-та и трябва да си остане двуезичен.

Две неща не се променят със задна дата, и това е нарочно:

ranking.explanation се записва при класиране. Класиранията отпреди смяната носят стария текст, докато не бъдат преизчислени — за одитната следа това е правилното поведение.
Активирана версия правила не се редактира, така че име като „Базови правила за инженерни роли“ си остава в базата. Ново име значи нова версия — виж раздела за правилата.

Панелът за решение няма предварително избран статус и записът е блокиран, докато няма и трите: статус, обосновка и име на рекрутера. Името се въвежда в хедъра („Вие сте") и се пази локално — проектът няма аутентикация, а „system" в графата „кой потвърди" би било невярно.

bash
cd frontend
cp .env.example .env      # VITE_API_URL сочи към бекенда
npm install
npm run dev               # http://localhost:3000
npm test                  # тестове на потока за решение и на API слоя
npm run build             # статичен билд в dist/

Произходът на изгледа трябва да е в cors_origins на бекенда (виж backend/app/core/config.py) — портовете 3000 и 5173 са там по подразбиране.

Seed данни

Синтетичен набор за разработка и демо: една активна версия правила, две роли и шест кандидата. Пуска се ръчно и е идемпотентен — повторното изпълнение обновява, вместо да дублира (ключът е external_ref):

bash
docker-compose exec backend python -m app.seed   # в контейнер
python -m app.seed                               # локално, от backend/

Кандидатите се раждат от суров CV текст през същия парсер като продукционния път, а защитените признаци (пол, възрастова група, произход) се попълват само тук — те не идват от CV-то и служат единствено на bias-одита. Всички данни са измислени.

След seed класирането е на един curl разстояние:

bash
curl -X POST http://127.0.0.1:8000/roles/<role-id>/rank

Тестове
bash
docker-compose exec backend pytest   # бекенд
cd frontend && npm test              # изглед

Покрити са ключовите елементи: логиката на скоринга, explainability изходът, bias-одитът, и от двете страни — че решение без човек и без обосновка не се записва.
